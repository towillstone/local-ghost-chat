# Local Ghost Chat

A static college project starring **Ghost of UCF**, a fictional eternal student with a fondness for Knights football, coffee, and parking jokes. The interface uses an original CSS ghost illustration. All generated replies run on the visitor's CPU inside a browser Web Worker.

## Model and Mac requirements

- Model: `onnx-community/SmolLM2-135M-Instruct-ONNX`, converted from Hugging Face's Apache-2.0 SmolLM2-135M-Instruct model.
- Library: Transformers.js **3.8.1**, pinned on jsDelivr.
- Runtime: ONNX Runtime Web, **WebAssembly**, one CPU thread. This avoids requiring WebGPU or special cross-origin isolation headers that GitHub Pages cannot configure.
- Precision: `q8`, selecting `onnx/model_quantized.onnx`, approximately **136 MB**. Configuration and tokenizer files, JavaScript, and WASM add overhead. Budget roughly **150–180 MB on first load**, and at least **200 MB of browser cache space**. Total transfer is an estimate, so record the actual transfer on your machine.
- Memory: allow approximately **0.5–1.5 GB free memory** as a planning estimate for weights, runtime buffers, activations, and short context. This has not been measured on your Mac. A Mac with **8 GB RAM or more** and current Chrome or Edge is a practical starting point. CPU inference also works without Apple Silicon, but speed and available memory vary. Try Safari separately and record compatibility rather than assuming identical results.
- Model files are cached when the browser supports and retains Cache Storage. Clearing site data, private browsing, or storage eviction can force a download again.
- This very small model trades response quality for download size. Character consistency, factual accuracy, and humor are experimental. It has no access to live campus information. The prompt requests short, kind replies and honest uncertainty, but compliance is not guaranteed.

The character instruction is at the top of `worker.js`. Each generation includes that instruction, up to two previous conversation turns, and the newest user message. Input is limited to 400 characters and output to 100 new tokens. Adjust the instruction to explore intentionality and character voice.

## Data flow

1. GitHub Pages serves the HTML, CSS, and JavaScript.
2. Only after the visitor clicks **Wake the ghost**, a module worker imports Transformers.js from jsDelivr and downloads model assets from Hugging Face. Those services receive normal asset requests, including connection metadata.
3. Typed chat messages go through `postMessage` to the local worker, then into the local generation pipeline. There is no inference endpoint, API key, analytics, or chat upload code.
4. Replies are inserted with `textContent`. Chat history lives only in memory, clears on refresh, and can be cleared with **Clear chat**. Model cache is separate and is not removed by clearing chat.

The opening greeting is explicitly labeled scripted. Replies labeled AI response are generated by the model. Errors are displayed as errors, without substitute canned replies.

## Run locally

Serve this folder with a static HTTP server. If Python 3 is installed:

```sh
cd /path/to/local-ghost-chat
python3 -m http.server 8000
```

Open `http://localhost:8000`. Use HTTP localhost or HTTPS hosting. Opening `index.html` through `file://` can block module workers. An internet connection is needed for initial asset downloads. Do not promise offline page reloads because there is no offline service worker.

## Deploy to GitHub Pages

1. Create a repository named `local-ghost-chat` on GitHub. A public repository works with GitHub Free.
2. Upload the **contents** of this folder to the repository root. `index.html`, `style.css`, `app.js`, `worker.js`, and `.nojekyll` should be alongside one another, not nested inside another folder. Include this README if desired. No model weights or node_modules need uploading.
3. Commit the files to `main`.
4. Open **Settings → Pages → Build and deployment**.
5. Choose **Deploy from a branch**, select **main** and **/(root)**, and click **Save**.
6. Wait for the Pages workflow to succeed. Open the URL shown in Settings. For the GitHub account used in the earlier quiz, the expected URL would be `https://towillstone.github.io/local-ghost-chat/`. This URL is an example until deployment succeeds.
7. Test the deployed URL, especially model download and one generated response. Relative paths support GitHub Pages repository subdirectories.

No build command, paid hosting, backend, or cloud AI subscription is required. The source files are available in this repository. Enable GitHub Pages using the steps above to publish the project.

## Test plan

Record the browser version, macOS version, Mac chip, installed RAM, connection, and whether assets are cached.

1. **Initial state.** Open the site. Confirm Model not loaded, disabled composer, visible character/model description, and a clearly labeled scripted greeting. Model download should not begin until Wake the ghost is clicked.
2. **Cold load.** Click Wake the ghost. Watch loading, per-file progress, initialization, and Ready. Progress describes the current file, not a combined download percentage. Record the displayed load time and Network panel transfer size.
3. **Generated reply.** Ask `Tell me a ghost joke about campus parking.` Confirm Thinking, an AI response, Ready, and the reply duration. Allow time on CPU, potentially tens of seconds or longer depending on the Mac.
4. **Topics and voice.** Ask about game day and surviving finals. Record whether the answer is funny, helpful, relevant, and recognizably Ghost of UCF. Save an unedited example of a weak answer too.
5. **Conversation.** Say `My name is Sam`, then `What is my name?` Check short-context recall. After several turns, older turns are intentionally discarded. Clear chat and verify the visible conversation resets.
6. **Current facts.** Ask `What was the score of the latest UCF game?` Record whether it admits uncertainty or invents information. Check factual claims against an official source if using them in your reflection.
7. **Input behavior.** Try empty spaces, Enter, Shift+Enter, the 400-character limit, and rapidly clicking Send. Confirm only one request runs at once. Text such as `<b>boo</b>` should display as text.
8. **Keyboard and layout.** Tab through controls, look for visible focus, and test at a phone width of about 390 pixels. Confirm no horizontal overflow and readable message wrapping.
9. **Cached load.** Refresh and load again. Compare load time and transferred bytes with the first run. Cached weights still need initialization in memory.
10. **Local inference check.** Load the model and get a reply first. In browser developer tools, set Network to Offline while keeping the tab open, then send a new prompt. A successful new reply demonstrates local generation with the loaded model. Look for no requests containing prompt text and no inference endpoint. Restore networking before refreshing. If an asset was lazily loaded and this fails, record it honestly and investigate the Network panel.
11. **Failure handling.** In a fresh browser profile or after clearing this site's cached data, switch Offline before loading. Confirm an error and Retry loading. Restore networking and retry. Failed generation keeps the question in the input for retry. If the worker crashes, reload/reinitialize the model.

## Verification performed for this delivery

The implementation was reviewed for relative asset paths, worker-based inference, bounded history, user-input text insertion, loading/error states, and lack of an inference API. Browser generation and visual QA could not be completed in the authoring environment because localhost server binding was denied, including after a network permission request. The shell also lacked a working Node or Python runtime, and the embedded runtime blocked dynamic syntax compilation. Run the checks above before submitting. No performance or memory benchmarks are claimed.
